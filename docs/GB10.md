# gb10 imputation backend

Enable it on a future harness invocation with `--impute-backend gb10`.
The gb10's address, account and ssh key path are not in the repository. They are
read from a private file, `~/.config/prs-harness/gb10.json` (override the path
with `PRS_HARNESS_GB10`), mode 600, like the launch-gate tokens:

```json
{"host": "<account>@<address>", "identity": "/absolute/path/to/the/ssh/key",
 "dev_cases": ["<persona id>", "..."]}
```

`dev_cases` is the dev allow-list: the only cases whose genome may go to the
gb10. A held-out case never goes there, since the gb10's own agent can read
anything under that account. The case id is the persona's own `persona_id`; a
human backend has none and is refused. A gb10 run with no such file, with a
field missing or malformed, or for a case not on the list does not launch, and
the refusal is recorded in its manifest before anything is staged; there is no
default. Then, still before staging, the key is checked (a regular file only
this account can read; it is never opened) and the gate is pinged with it. A
gb10 that does not answer `ok`, or a key that is missing or open to others,
stops the run from launching. The destination is the installed restricted gate.
Every run, on either route, puts `~/.ssh` and the configured key on its denial
probe list, so each run proves no sandbox can read the key; a config file that
exists but cannot be read stops the run rather than leaving the key unprobed.
SSH requires an existing trusted host key, uses batch mode, and has connection
and liveness deadlines. ssh's and Beagle's error text is recorded with the
address and account replaced by `<gb10>`. This change does not install or
modify the remote gate.

The harness decides where Beagle runs, and the agent cannot override it. It
writes `{"backend": "gb10"}` (or `"local"`) to `refdata/imputation.json`, inside
the read-only bind, and `impute_joint.py` reads it; the tool has no option that
overrides it, and with no file (outside the harness) it is local. On the gb10
route the refdata clone has no `bin/beagle.jar` and no bundled `jre/`, and the
PRS profile hides `/usr/lib/jvm` under an empty read-only tmpfs, so nothing in
the sandbox can run Beagle and nothing can fall back to this machine. The launch
gate's denial probe proves it each run: the clone's jar and JVM, the original
jar and this machine's resolved `java` must all be unreachable from the PRS
sandbox. The score skill does not name the switch. The score command,
patient/cohort split, seed, GP, DR2, sample count checks and downstream
artifacts are unchanged. The SSH key and host client stay outside the sandbox;
the agent has no general remote-command interface.

Each merged target is restricted to its chromosome before upload. Inputs must
resolve inside the requesting run, are copied through checked file descriptors
into private host scratch, and are checked again for other chromosomes before
`put-gt`. Only fixed, validated gate requests leave the host. There are two
chromosomes in flight, one compute operation and one download at a time. Each
chromosome receives its own gate run ID, so the run lock held by one download
does not block computing the next chromosome. Threads are fixed at **6**; the
gate sets the JVM heap to 10 GiB. Local JVM options cannot change the remote JVM.

The download is spooled to a temporary file. Its two expected regular tar members
are copied as bytes into fixed local filenames: ownership, mode, links and paths
from the archive are never applied. Both members and the completed Beagle log
must validate before delivery, and the VCF must decompress to its end with
every gzip member's CRC and length intact. The host then copies the files into a
fixed location inside the run, and the imputation tool moves them to
`cohort/chr<N>.cohort.vcf.gz` and `cohort/chr<N>.cohort.log`, where Beagle writes
them on this machine. The gate does not keep Beagle's stdout, which
`chr<N>.beagle.log` holds locally; the log carries the same lines, sample counts
included, so `chr<N>.beagle.log` is built from it under a line naming the gate
run. Every file a local run leaves in `--out-dir`, the gb10 route leaves too.

Waiting and retrying follow the design. ssh runs with `ConnectTimeout=30` and
`ServerAliveInterval=60`. A connection failure (ssh exit 255) is retried three
times, after 30 s, 2 min and 5 min. Busy (exit 6: the box's one Beagle slot, or
the id's lock) is polled every 60 s; an upload gives up after 30 min and a
download after 30 min, and `run` waits up to 3 h 15 min for the slot, since
another job can hold it for at most the gate's 3 h. A running `run` gets 3 h
10 min. If its connection drops, it is never sent again: Beagle may still be
running there, so `get` is polled every 60 s -- 6 still running, 0 collected
(that archive is the output), 5 Beagle did not finish, a failure -- until the
gate's own timeout (3 h + 60 s) has passed since the `run` was sent. A `run`
whose ssh never reached the gate (`ssh: connect to host ...`, a refused key) ran
nothing there and is sent again on the same schedule. Nothing else is retried:
2, 3, 4, 7, a 5 after a successful `run`, or Beagle's own exit status.

Every allocated gate ID is registered before the first upload. Each chromosome
cleans its ID in `finally`, including failed uploads and downloads. `clean` is
retried, busy or ssh failure alike, for at least 10 min, and while Beagle may
still be running for that id -- a `run` whose end was never seen -- until the
gate's own timeout has passed since it was sent, because that Beagle holds the
id's lock and `clean` answers busy until the gate stops it. Harness shutdown
drains workers and retries every ID whose cleanup has not succeeded; a failure
on one ID does not skip the others. The gate has no cancel command, so shutdown
waits for an active compute request to release its lock instead of assuming that
killing SSH kills Java. An id still not cleaned after all that is recorded, with
its error, in the manifest's `cleanup_failures` and a caveat. No cleanup success
is inferred from a lost connection. The gate's day-old sweep remains a last
resort, not the normal cleanup path.

`impute_joint.py` waits up to 24 h for each chromosome's reply. That is longer
than the gate client's worst case for one chromosome queued behind another,
about 19.5 h (`GateClient.worst_case_seconds()`), so the sandbox never gives up
on a request the harness is still working on; the run's own time cap ends a run
long before that.

Per-chromosome upload/download bytes, SHA-256 digests, elapsed request times,
retry counts, gate ID and cleanup status are recorded in `impute_joint.json` and
host receipts under `vault/runs/<run>/imputation/`. The manifest's `imputation`
block records the route, each request with the threads and seed it asked for,
and under `impute_joint_runs` the threads, seed, route and counts each run of
`impute_joint.py` recorded itself; the harness assumes no thread count. Private
scratch is deleted when the request ends.

A gb10 failure ends the run as an environment failure. The broker tags every
failed request with whose failure it was: `request` for the agent's own request
or files (a path outside its run, an input that is not one chromosome), `closing`
when the harness stopped it because the agent's run had ended, and `gb10` for
everything else (the gb10 or the network, the gate, Beagle there, a download that
does not validate, its delivery here). On the first `gb10` failure
`impute_joint.py` sends and waits for nothing more, runs nothing locally, writes
`impute_joint.json` with `gb10_failure`, and exits non-zero; the score skill
tells the agent to write no result, say why and end the run. The harness then
reads `manifest["imputation"]["requests"]` in `gb10_blocked_reason()`, part of
`environment_failure()`, and files nothing under `results/`: `gb10 blocked:
chr<N> <reason>`. As with the provider, a run that still wrote a valid result is
filed as the agent's result, and so are `request` and `closing` failures.

## Verification without a real run

All fixtures are synthetic. These tests make no SSH connections:

```bash
PYTHONDONTWRITEBYTECODE=1 \
BEAGLE_JAR=/path/to/beagle.jar \
GB10_GATE_SCRIPT=/path/to/installed/gate.sh \
python3 -m unittest discover -s tests -v
```

The chromosome-cut test compares all 300 Beagle record lines, including
GT/DS/GP/DR2/IMP, between the old whole-genome target and the sliced target.
The full-tool test compares cohort records, patient records and DR2 tables for
two chromosomes (600 sites), through local execution and the broker. When
`GB10_GATE_SCRIPT` is set, that test uses a disposable local copy of the actual
gate with only its root and minimum free disk setting changed, and real Beagle.
Otherwise it uses a local gate double. The tests also cover actual run locks,
concurrent download/compute, unsafe archives, busy retries, cancellation,
timeouts, cleanup failures, sandbox path escapes and remote failure propagation.
Java/Beagle or bcftools being absent skips the scientific identity checks; a
passing transport-only suite does not establish identity.
